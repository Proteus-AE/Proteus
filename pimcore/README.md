# PimCore

Standalone C++17 simulation core for ProteusSim, dependency-free (own
YAML-subset configuration loader, CMake build). Two engines share one
codebase:

**Command-level memory backend** (`src/channel.cpp`, `src/bank.cpp`, ...):
event-driven per-channel model of the near-bank PIM substrate -- per-bank
row-state machines under the full DRAM timing table
(tRCD/tRP/tRAS/tRC/tCCD/tWTR/tWR/tRRD/tFAW/tREFI/tRFCab), time-multiplexed
bank-group data buses, aligned all-bank refresh, per-bank PE pipelines with
operand-FIFO back-pressure, direct/broadcast connectivity with drained mode
switches, in-place KV-append writes, and DRAMPower-style per-command energy.
Three substrate tables ship in `configs/`: LPDDR5X-PIM (Proteus), HBM-PIM,
and GDDR6-AiM class devices. A host-path memory controller (`controller.cpp`,
`traffic.cpp`, `device.cpp`) schedules xPU traffic against the PIM stream
under FR-FCFS with three arbitration policies (PIM-priority / interleave /
host-priority), reporting host latency histograms and PIM slowdown.

**Operator-level system layer** (`src/syscore.cpp`): the decode-iteration
timing/energy models of Proteus (co-execution split, in-flight batching,
incremental variants, device scaling, [PP, DP] hybrids) and the six baseline
systems, consuming the repository's `configs/` YAML files directly. It is an
independent implementation of the Python system layer; the cross-check
(`experiments/run_sys_crosscheck.py`) verifies the two against each other on
every evaluation cell.

## Build and run

```bash
mkdir -p build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release && make -j
./pimcore_tests                       # 20 test groups

# memory backend
./pimcore --config ../configs/lpddr5x-8533.yaml --kernel gemv --rows 96
./pimcore --config ../configs/lpddr5x-8533.yaml --kernel skinny-gemm \
          --rows 64 --vectors 8 --mode broadcast --json
./pimcore --config ../configs/hbm-pim.yaml --kernel attention --group 8

# co-execution policy sweep (CSV on stdout)
./pimcore_coexec --config ../configs/lpddr5x-8533.yaml --rows 48 --vectors 8

# operator-level system layer
./pimcore_sys --configs ../../configs                     # overall tables
./pimcore_sys --configs ../../configs --table breakdown   # Sec. V-C
./pimcore_sys --configs ../../configs --table sensitivity # Sec. V-D
./pimcore_sys --configs ../../configs --table scalability # Sec. V-E
./pimcore_sys --configs ../../configs --system proteus \
              --model mixtral-8x7b --batch 32 --variant rd

# closed-loop continuous-batching serving (CSV per iteration)
./pimcore_serve --configs ../../configs --model mixtral-8x7b --batch 32 \
                --prompt-mean 2048 --out-mean 256 --iters 600
./pimcore_serve --configs ../../configs --model mixtral-8x7b \
                --trace ../../request_traces/pool256.txt

# trace generation: PIM kernel traces and host-path address streams
./pimcore_tracegen --kernel skinny-gemm --rows 64 --vectors 8 \
                   --mode broadcast -o gemm.trace
./pimcore_tracegen --host-stream --pattern random --reqs 200000 \
                   --style ldst -o host.trace

# host-only traffic (the external cross-check configuration)
./pimcore_coexec --host-only --pattern stream --offered 20 --duration-us 400
```

The Python layer drives all of this through
`proteus_sim/dram/pimcore_bridge.py` (build-on-demand + JSON reports); the
trace format is shared with the Python backend, so traces generated by
`trace_gen/` replay on either engine.
